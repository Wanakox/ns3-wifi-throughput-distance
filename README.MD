# NS-3 WiFi Throughput vs Distance Demo

## 1. Project Overview

This project implements a practical NS-3 simulation to study the performance of a basic WiFi network as the distance between the Access Point (AP) and the Station (STA) changes.

The main goal of the demo is to analyze how distance affects the quality of a wireless link. In particular, the simulation measures three Key Performance Indicators (KPIs):

- **Throughput** in Mbps
- **Average delay** in ms
- **Packet loss** in %

The scenario is intentionally simple: one WiFi Access Point and one WiFi Station. The station sends UDP traffic to the access point while the distance between both nodes is varied across several experiments.

The project's topic is:

> Simulation of WiFi Network Performance using NS-3: Throughput vs Distance

The practical objective is to verify how signal degradation, propagation loss, and traffic load affect the effective performance of a wireless link.

## 4. Demo Concept

The objective of this demo is to study how the distance between a WiFi Access Point (AP) and a WiFi Station (STA) affects the performance of a wireless link.

The simulated topology is intentionally simple:

```text
WiFi Station  <--------- variable distance --------->  WiFi Access Point
```
The Access Point remains fixed, while the Station is placed at different distances depending on each experiment. During the simulation, the Station sends UDP traffic to the Access Point. At the end of each run, the simulation exports the measured performance values to a CSV file.

The main Key Performance Indicators (KPIs) evaluated are:

- **Throughput**, measured in Mbps.
- **Average delay**, measured in milliseconds.
- **Packet loss**, measured as a percentage.
- **Transmitted and received packets**, used to support the packet loss calculation.

The purpose of using this basic topology is to isolate the effect of distance and traffic load on WiFi performance. This makes the experiment easier to reproduce and analyze, while still representing a relevant wireless networking problem.

## 7. Test 1: Initial Simulation Configuration

In the first version of the simulation, the WiFi channel was created using the default YANS WiFi channel configuration and then an additional `LogDistancePropagationLossModel` was added.

The relevant part of the initial configuration was:

```cpp
YansWifiChannelHelper channel = YansWifiChannelHelper::Default();

channel.AddPropagationLoss("ns3::LogDistancePropagationLossModel",
                           "Exponent",
                           DoubleValue(3.0));
```

This configuration produced a very aggressive degradation of the wireless signal. The results showed that the connection collapsed at very short distances, with packet loss reaching 100% in many cases.

Although this first configuration did not produce a gradual degradation curve, it was useful as an initial experiment. It showed that the propagation model and channel configuration have a strong impact on the simulation results.

The outputs of this first version are stored in:

```bash
results/test_1/
plots/test_1/
```

## 8. Test 2: Improved Simulation Configuration

After analyzing the results obtained in Test 1, the simulation code was modified to obtain a more controlled and realistic behavior. In the first version, the signal degradation was too aggressive, causing the WiFi connection to collapse at very short distances. Because of this, a second version of the simulation was created.

The improved version explicitly defines the propagation delay model, the propagation loss model, and the transmission power:

```cpp
YansWifiChannelHelper channel;

channel.SetPropagationDelay("ns3::ConstantSpeedPropagationDelayModel");

channel.AddPropagationLoss("ns3::LogDistancePropagationLossModel",
                           "Exponent",
                           DoubleValue(2.0),
                           "ReferenceDistance",
                           DoubleValue(1.0),
                           "ReferenceLoss",
                           DoubleValue(46.6777));

YansWifiPhyHelper phy;
phy.SetChannel(channel.Create());

phy.Set("TxPowerStart", DoubleValue(20.0));
phy.Set("TxPowerEnd", DoubleValue(20.0));
```

The main changes introduced in Test 2 were:

1. The default YANS channel was replaced by an explicit channel configuration.
2. The path loss exponent was changed from `3.0` to `2.0`.
3. The reference distance and reference loss were explicitly defined.
4. The transmission power was fixed at `20 dBm`.

These changes reduce the excessive degradation observed in Test 1 and provide a better baseline for studying the relationship between distance and WiFi performance.

The outputs of this second version are stored in:

```text
results/test_2/
plots/test_2/
```

## 9. Traffic Load Configuration

The UDP traffic load is controlled using the packet interval parameter. This value defines how often the UDP client generates packets.

The offered load can be approximated as:

```text
Offered load = packet size × 8 / packet interval
```

Using a packet size of `1024 bytes`, the approximate offered load is:

| Packet Interval | Approximate Offered Load | Interpretation |
|---|---:|---|
| `0.0002 s` | 40.96 Mbps | High load |
| `0.001 s` | 8.192 Mbps | Lower load |

A smaller packet interval means that packets are generated more frequently. Therefore, the offered traffic load increases.

A larger packet interval means that packets are generated less frequently. Therefore, the offered traffic load decreases.

This distinction is important because WiFi performance depends not only on distance, but also on the amount of traffic injected into the network. If the offered load is too high, the network can become saturated and produce high packet loss, high delay, or unstable throughput even at short distances.

| Column | Meaning |
|---|---|

The CSV files are useful because they provide the raw numerical data used to generate the plots. This makes the experiment reproducible and allows further analysis if needed.

## 14. Result Interpretation

The practical demo shows that WiFi performance is the result of several interacting factors, not only the physical distance between the Access Point and the Station. The initial expectation was that throughput would progressively decrease as distance increased. However, the experiments showed that this behavior depends strongly on the channel configuration and on the offered UDP traffic load.

The comparison between `test_1` and `test_2` was especially important. In the first configuration, the propagation model was too aggressive and the link degraded too abruptly, which made it difficult to observe a meaningful throughput-versus-distance trend. After modifying the channel configuration in `test_2`, the simulation became more stable and easier to interpret. This shows that the propagation model, path loss exponent, reference loss, and transmission power are not secondary details; they directly determine whether the simulation produces useful and realistic results.

The results also show that traffic load can dominate the behavior of the network. Under lower offered load, the WiFi link was able to maintain stable throughput and very low packet loss across the tested distances. In contrast, under high offered load, the throughput remained limited by the capacity of the simulated link, while packet loss and delay increased significantly. This means that performance degradation is not always caused by distance alone; it can also appear because the network is saturated by excessive traffic.

Therefore, the most important conclusion of the demo is that throughput must be analyzed together with delay and packet loss. A throughput value by itself does not fully explain the state of the network. High packet loss or high delay can reveal congestion, saturation, or poor channel conditions even when throughput appears stable.

Overall, the experiment confirms the usefulness of NS-3 for controlled wireless network analysis. It allowed the same topology to be tested under different distances, traffic loads, and propagation configurations. The practical lesson learned is that a valid wireless simulation requires both theoretical understanding and careful parameter selection. In WiFi networks, distance matters, but the final performance also depends on how the channel is modeled and how much traffic is injected into the system.
